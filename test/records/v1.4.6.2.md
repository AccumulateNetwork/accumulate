## What this release contains

Delta measured against **`v1.4.6`**.

### `#4074` — v3 receipt queries hang for old chain entries (the reason for the release)

`SearchIndexChain` walked index chains linearly, one database read per entry,
carrying a `TODO Add a guard to prevent scanning the entire chain?`. Receipt
assembly starts its searches at the newest index entry, so a receipt for an
entry with an old anchor scanned from the chain head back to that anchor —
hundreds of thousands of reads on a real network.

| symptom | cause |
|---|---|
| old-anchor receipts hang; fresh ones return in ~0.5s | scan length equals the distance from chain head to the entry's anchor |
| hung forever on HDD, seconds-to-minutes on SSD | 300k+ random reads |
| node memory grew to 25G RSS | every read is cached in the request's `database.Batch` |
| kept computing after the client disconnected | nothing on the path checks the request context |

Index chains are ordered and all four search predicates are monotone, so the
search is now a binary search: O(log n) reads. Semantics are preserved exactly
— `internal/database/indexing/chain_test.go` runs the new implementation
against the original linear one as an oracle across chain sizes, match modes,
start positions and every predicate.

### `#4076` — flaky `TestVersionSwitch`

Activating a protocol version normally converges in ~17 simulator steps but
sometimes takes exactly 75; `StepUntil`'s default budget of 50 fell between the
two modes. The budget is now a hang guard, not a number tuned to observed
performance — how many steps an activation takes is not part of what the test
asserts.

**The underlying cause is not fixed** and remains open as `#4076`: simulator
message ordering is nondeterministic. Conductor background tasks run
concurrently through an `errgroup`, `Simulator.Step` carries a `TODO Care about
s.deterministic` so the `Deterministic()` option is accepted but ignored, and
`orderMessagesDeterministically` is never called outside its own unit test.

## Verification

### CI

Pipeline #16230 on the tag: all 11 jobs green, including both `go test` shards.

### Deployed and measured on Kermit

The node binary in `v1.4.6.2` is **identical** to `v1.4.6.1` — the only
difference between the two tags is `multi_test.go` and `CHANGELOG.md`, so the
deployment evidence below transfers.

Kermit (server4, DN height ~6.32M) upgraded from the pre-fix binary. The
reporter's own repro queries, on the node and through the public URL:

| query | before | after (local) | after (public) |
|---|---|---|---|
| old keypage entry + `includeReceipt:true` | 8.7s on SSD, hung >180s on HDD | **0.0076s** | 0.128s |
| `dn.acme` main `index:0` + `includeReceipt:true` | **never returned** | **0.0064s** | 0.136s |
| same entry + `includeReceipt:{forAny:true}` | hung >180s | **0.0022s** | — |
| control: same entry, no receipt | ~281ms | — | 0.242s |

Receipts are correct, not merely fast: the first returns the same
`localBlock: 14526` it produced before the change.

Memory: previously two receipt queries took the node from ~2G to 25G RSS.
Across all three receipt queries above, RSS moved 8.885G → 8.900G (+14MB).

Post-upgrade health: all three nodes resumed from their pre-shutdown height
with no data loss, consensus advancing, faucet round-trip delivered
cross-partition in ~10s.

## Not covered

- **Mainnet is not on this release.** It carries the same `#4074` defect with
  deeper index chains (DN ~32.5M blocks vs Kermit's ~6.3M). v1.4.6.2 was built
  and tagged for Kermit testing, not as a mainnet deployment.
- **The `#4074` follow-ups are not done**: request-context cancellation through
  the receipt path, a server-side deadline on API queries, and bounding the
  `database.Batch` record cache for read-only API batches. The binary search
  removes the acute problem; those three bound *every* slow query.
- **Simulator determinism** (`#4076`) is worked around, not fixed.
- Sub-logarithmic index lookup was considered and declined — see the design
  note on `#4074` for why interpolation, a fitted/learned index, and reusing
  `merkle.ChainIndex` were each rejected.
- No load, soak, or multi-node deployment testing was run against this tag
  beyond the single-host Kermit devnet.
