# Execution sharding A/B, 2026-08-25

Paired runs [20260825T212353Z](20260825T212353Z/manifest.md) (shards=1) and
[20260825T214853Z](20260825T214853Z/manifest.md) (shards=8). Same commit
(`32217c903`), same topology (2 BVNs x 4 validators), same rate (250 tps
target), chaos off, fresh genesis each. One variable: `ACC_EXECUTION_SHARDS`.

## Result

| | A: shards=1 | B: shards=8 |
|---|---|---|
| achieved rate | 230.5/s | **230.7/s** |
| generated | 262,571 | 263,229 |
| rejected / backpressure | 0 / 0 | 0 / 0 |
| envelopes executed (fleet) | 1,294,476 | 1,297,184 |
| sharded | 0 (0.0%) | **1,215,786 (93.7%)** |
| shardsUsed (max) | 0 | **8** |
| DN height | 8 -> 405 | 8 -> 405 |
| stalled channels at end | 4 | 4 |
| live heap | 653-726 MiB | 818-856 MiB |
| RSS | 1.00-1.15 GiB | 1.13-1.19 GiB |

**Sharding works and changes nothing here.** 93.7% of envelopes executed in
parallel across all 8 shards, and throughput, block height and channel state
are identical to the serial arm. Execution was not the constraint at 230 tx/s.

Two block populations, as the design predicts: user-traffic blocks (~180
envelopes, ~95% sharded, all 8 shards used) and anchor/synthetic blocks (~18
envelopes, 100% serial by construction — hazard (i)).

## What this does NOT show

**Neither arm was driven to its limit.** 0 rejected and 0 backpressure in both.
The rate sat at ~230 against a 250 target because the LOADGEN skipped ~6,400 of
its own attempts, not because the network pushed back. A ceiling was never
reached, so this says nothing about whether sharding raises one.

The 250 target was chosen because the 20260825T140034Z ladder hit backpressure
at that rate. That was a misreading of our own evidence: that run reached 250
after 45 minutes at 100 tps with ~25k accounts built up. Backpressure there was
STATE-dependent, not rate-dependent. Cold at 250, both arms are comfortable.

To measure a ceiling, both arms must be laddered past 250 until they break.

## Cost of sharding

Live heap rose ~90-130 MiB (roughly 15%) at 8 shards — the per-shard child
batches hold their memoized working sets concurrently rather than one at a
time. Not free, but not the per-shard multiple of the process footprint that
was feared before it was measured.

## Harness bugs found by these runs

1. **`DURATION=30m` silently ran 20 minutes of load.** soak.sh applies the
   short-run timeout at `duration_seconds -le 1800`, and 30m is exactly 1800,
   so `LG_TIMEOUT=20m` wins over `-duration 30m`. Both arms were treated
   identically so the comparison holds, but a run does not last what it says.

2. **`.dockerignore` does not exclude `test/docker/soak/runs`, now 96 GB.**
   Every `compose build` carries the whole soak archive: ~10 minute builds, and
   the image ID changes on every run even when the source does not. That makes
   image id useless as an identity for the binary — arm A built `74ef6986`,
   arm B `6ab4b3a6`, from identical source. Arm A's image was replaced before
   the two binaries could be diffed, so this A/B rests on the source being
   identical (verified) rather than the binaries (not verified).

3. **The per-worker metrics have never emitted.** `worker_batches_created_total`,
   `worker_transactions_received_total`, `worker_pending_transactions` and two
   more are defined with `worker_id` labels and setters in
   `pkg/consensus/metrics/metrics.go`; the setters are called only from
   `metrics_test.go`. They export no series, which is why `/metrics` has no
   `worker_*` at all.

## Related, proven separately (#4133)

`api.go` computes `routeKey := signerOf(envelope)` and then calls
`SubmitTransaction(b)`, which is `SubmitTransactionFor("", ...)`.
`routingKeyBytes("")` returns nil, so `workerFor(nil, 4)` is a constant:

    workerFor(nil,  4) = 1     every submission, always
    workerFor(nil, 64) = 37
    alice->2, bob->3, carol->1  (real keys spread correctly)

Worker 1 takes 100% of traffic; workers 0, 2 and 3 are idle batch-timer loops.
This is a serialization in FRONT of execution and is untouched by these runs.
